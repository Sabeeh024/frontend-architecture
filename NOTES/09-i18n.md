## The two decisions, now proven out

**Message catalog = a plain module.** `shared/i18n/messages/en.js` and `es.js`
— flat key → string maps. The only files a translator (or a translation
service) ever touches; no JSX, no logic.

```js
// en.js
'comments.count.one': '1 comment',
'login.welcome': 'Welcome, {name}',
```

**Current locale = a store, not Context.** Same reasoning as `authStore` in
topic 06: a production app's route **loaders** would need to read the locale
before any component renders — e.g. a URL like `/es/posts/p1` deciding what to
fetch and how to format it — and loaders can't `useContext`. `localeStore.js`
persists to `localStorage`, same pattern as `ThemeProvider`... except theme
stayed in Context (topic 06) because nothing outside React needs it. Locale
*would* be needed outside React in a real app, so it goes where auth went.

## The API (`shared/i18n/t.js`)

```js
export function t(key, vars) { … }          // plain function — loaders, formatDate, stores
export function tn(key, count, vars) { … }  // key.zero / key.one / key.other
export function useT() { … }                // hook: subscribes, re-renders on switch
export function useTn() { … }
```

`t`/`tn` read `getLocale()` directly (module-level, no subscription) — safe to
call from anywhere, but won't trigger a re-render on their own. `useT`/`useTn`
add exactly one thing: `useLocaleStore((s) => s.locale)` to force the
component to re-render when the locale changes. Components use the hook forms;
non-component code (a loader, `formatDate`) uses the plain functions.

```jsx
// features/comments/ui/Comments.jsx
Comments.Count = function Count() {
  const { comments } = useCtx()
  const tn = useTn()
  return <>{tn('comments.count', comments.length)}</>   // "No comments" / "1 comment" / "3 comments"
}
```

Interpolation is `{name}` string replacement — no ICU. Pluralization is
zero/one/other — enough for English and Spanish, **not enough for languages
with more plural categories** (Arabic has six, Polish four). That's a
deliberate simplification: the point here is the *architecture* (where the
catalog lives, where the locale lives, how a component asks for a string), not
reimplementing CLDR. A production app takes this exact shape and swaps `t.js`
for `react-intl` / `next-intl` / `lingui`, which is where real ICU MessageFormat,
CLDR plurals, and number/currency/date formatting come from.

## `formatDate` — closes a real gotcha from topic 08

Topic 08 flagged `formatDate` as secretly impure: it called
`toLocaleDateString(undefined, …)`, so its output depended on the *browser's*
locale, not anything the app controlled. Now:

```js
export function formatDate(iso) {
  return new Date(iso).toLocaleDateString(getLocale(), { … })
}
```

Switch the app to Spanish and every date re-renders as `20 ago 2026` instead
of `Aug 20, 2026` — verified in the browser. `shared/lib/formatDate.js`
importing `shared/i18n/localeStore.js` is `shared → shared`, so this doesn't
cost a single boundary rule from topic 07.

## What switching a locale actually touches

Clicked EN → ES in the browser:

- nav, headings, buttons, placeholders, toasts — all re-render translated
- `Comments.Count`: `"1 comment"` → `"1 comentario"` (still correctly singular)
- dates: `Aug 20, 2026` → `20 ago 2026`
- **zero network requests** — `RequestMeter` stayed at 1. Locale is pure client
  state; nothing about it should ever need a refetch (post/comment *content*
  isn't translated — that's real user data, not UI chrome)
- persists across reload (`localStorage`)
- post titles and bodies stay in whatever language the author wrote them —
  translating user-generated content is a different, much harder problem
  (machine translation, per-locale storage) that this topic doesn't touch

## The industry's approaches, category by category

What production i18n setups actually vary on — and, per category, whether this
repo now covers it or only describes it.

| # | category | common industry options | here |
|---|---|---|---|
| 1 | **message formatting library** | react-intl/FormatJS, i18next, Lingui (compile-time extraction), next-intl (Next-only) | ❌ described only — hand-rolled `t()`/`tn()`, `{var}` interpolation, zero/one/other pluralization (not real CLDR plural categories) |
| 2 | **locale in the URL** | path prefix (`/es/...` — Next.js i18n routing, most SEO-conscious sites), subdomain/domain per market, cookie/session only (no URL signal) | ✅ **implemented** — path prefix, this topic's second half |
| 3 | **where translations live / who edits them** | flat JSON/PO + a TMS (Crowdin, Lokalise, Phrase) syncing to/from it, in-context editing overlays, MT + human review for the long tail | ❌ described only — two hand-written `.js` files, no sync pipeline |
| 4 | **string extraction** | manual keys (what we did), compiler-extracted from inline default-locale strings (Lingui) | ❌ manual keys only |
| 5 | **rendering strategy** | client-only (ships every locale, decides at runtime), SSR/RSC per-locale (server picks the language, only that catalog ships, no flash), fully static per-locale builds | ❌ client-only — this is a Vite SPA, no server to render per-locale HTML |
| 6 | **CI enforcement** | catalog-drift check (missing/orphaned keys), lint against string concatenation bypassing the catalog, pseudo-localization builds to catch layout overflow | ❌ described only, flagged below |
| 7 | **beyond UI chrome** | translated *content* (data-modeling problem: locale-suffixed fields or a CMS, not a UI concern), RTL (`dir`, logical CSS properties), `Intl.NumberFormat`/`ListFormat`/`RelativeTimeFormat` | ❌ not touched — `formatDate` is the only non-chrome formatter here |

Row 2 is the one every guide agrees on regardless of stack, and it's also the
one that's pure **architecture** in this course's sense — a routing-as-
architecture question (topic 05), not a library choice. That's why it's the
one built for real here rather than described.

## Why URL-based locale, specifically, and what changed

The decision procedure was: of everything in the table, which is (a) close to
universal industry consensus, (b) changes *structure* rather than swapping an
implementation behind an already-correct seam, and (c) buildable without a
server this repo doesn't have? Only row 2 clears all three — a real ICU
library (row 1) is a drop-in replacement for `t.js` with no structural
change; SSR (row 5) needs infrastructure this Vite SPA doesn't have.

What moved:

```
before   locale lives in a store; URL never mentions it
after    locale lives in the URL (/:locale/...); the store *mirrors* it
         for the non-React code that still needs synchronous access
```

```js
// app/router.jsx — the whole tree, one level deeper
[
  { index: true, loader: () => redirect(`/${resolveLocale()}`) },   // once
  { path: ':locale', loader: localeLoader, element: <RootLayout/>, errorElement: <RouteError/>,
    children: [ /* every existing route, unchanged */ ] },
]
```

`localeLoader` does what any loader guard does (topic 06's `requireAuth` is
the template): validate before anything renders, and if invalid, `throw` — the
existing `errorElement` catches it, same as a missing post 404's.

```js
export function localeLoader({ params }) {
  if (!SUPPORTED_LOCALES.includes(params.locale)) {
    throw new Response('Not Found', { status: 404, statusText: `Unsupported locale "${params.locale}"` })
  }
  useLocaleStore.getState().setLocale(params.locale)
  document.documentElement.lang = params.locale
  return null
}
```

Every `<Link>`/`<NavLink>`/`redirect()` in the app needed the current locale
prefixed. Rather than hand-templating that at each call site, one hook:

```js
// shared/i18n/useLocalizedPath.js
export function useLocalizedPath() {
  const { locale } = useParams()
  return (path) => `/${locale}${path.startsWith('/') ? path : `/${path}`}`
}
```

used everywhere a path is built — `RootLayout`, `PostCard`, `PostPage`,
`Comments.Form`'s login link, `SettingsLayout`'s subnav, `routeGuards` (reads
`params.locale` directly since it's a loader, not a component).

**One deliberate exception:** `RouteError`'s "back to feed" link stays plain
`to="/"`. That page can be showing *because* `:locale` itself was invalid
(`/fr/...`) — building a link off the same broken param would produce another
dead link. `"/"` re-enters the redirect route, which re-resolves a real
locale from `localStorage`/browser language. Verified: visiting `/fr` 404s
with a working recovery link back to `/es` (the last valid locale).

**The locale toggle changed meaning.** It used to call `setLocale` directly —
now it navigates:

```js
const switchLocale = () => navigate(location.pathname.replace(`/${locale}`, `/${nextLocale}`) + location.search)
```

Switching language is a **navigation** (to the same page, under the other
prefix), not a silent state flip — `/es/posts/p1` → `/en/posts/p1`, verified
to land on the *same post*, not bounced to the feed. `localeLoader` re-syncs
the store automatically because the `:locale` param changed, so `formatDate`
and every `useT()` call site need zero changes.

**Testing:** `test/utils.jsx`'s `renderWithProviders` now wraps components in
a `<Route path=":locale/*">` so `useLocalizedPath` has a param to read even in
isolation; `router.test.jsx` gained a test for the unsupported-locale 404;
`routeGuards.test.js` asserts the redirect keeps the locale prefix. All 22
tests pass, lint/dependency-cruiser/build stay clean — this cost zero
boundary or cycle violations, because it's still `shared → shared` and
`app → shared/feature`, just one route level deeper.

## Next questions this raises

- **CI catalog-drift check** — diff `Object.keys(en)` against `es.js`, fail
  the build on a missing key. Small, and exactly topic 07's enforcement
  mindset applied to config instead of imports. The next concrete step.
- **A real ICU library** — swap `t.js` for `react-intl`/FormatJS behind the
  same `useT`/`t` call sites; correct plural categories, rich text,
  number/currency formatting come for free.
- **SSR / per-locale rendering** — out of reach without a server (Next.js,
  Remix); would remove the "ships every locale's JS" cost and the brief
  default-locale flash before the redirect resolves.
- Should tests run once per locale for components with pluralization/date
  logic, or is one (English) enough given the catalogs are data, not logic?
